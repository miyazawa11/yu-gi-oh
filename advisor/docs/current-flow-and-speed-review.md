# 現行仕様・処理経路・高速化とローカル知識の棚卸し

確認日: 2026-10-04。対象は作業フォルダー内のPython実装・CLI既定値・設定例・保存済み評価記録。実行中プロセスの引数や新しい対戦の動作は調査していません。本書作成では実装を変更せず、画面取得・ゲーム入力・外部API呼び出しも行っていません。

追記（同日、後続の実装変更）: 判断に10秒の期限を追加しました。期限・LLM再要求制限・予算切れでは、最新の許容候補から認識信頼度最高の行動を強制選択します。AI待ちのまま30秒停止する旧挙動は解消対象として実装済みです。以下の棚卸しは変更前の記録を含みます。最新の期限、例外、計測は[fast-loop.md](fast-loop.md)を参照してください。OCRの残り時間共有とrun側のAI完了・期限時の差分ゲート解除も追加しました。

## 結論

現在は「登録済みの画面領域を認識し、限定ルール・登録手順・任意のLLMで表示中の候補から選び、クリック後に確認する」構成です。対戦全体を理解する完成したルールエンジンではありません。認識・入力の枠組みはありますが、実デッキ、全ダイアログ、効果の使用履歴、分岐条件の整備と接続が不足しています。

速度改善は、計算高速化と、判断できず待っている状態の解消を分ける必要があります。優先候補は、LLMの再要求制限の見直し、確認条件の局所化、実画面校正と展開データの整備、画像保存の非同期化です。改善秒数は実対戦の計測前には確定できません。

## 1. 起動・運用機能

| 機能 | 現行実装 |
|---|---|
| run | 録画またはライブ画像から認識・推奨を生成。クリックしない |
| agent-loop | MSSで指定矩形を取得し、校正済み領域の中心をWindows APIでクリック |
| snapshot / calibrate-region / validate-calibration | 画像取得、領域と参照画像の登録、設定確認 |
| demo / evaluate / benchmark | 合成デモ、ラベル付きデータ評価、取得・再生の性能測定 |
| import-cards | カード情報JSONをSQLiteへ登録 |
| import-graph / graph-paths | 出典・条件付きのカード関係を保存し、深さ制限付き探索。自動判断には未接続 |
| export-dataset | 操作確認済みログを学習候補へ変換。最善手の正解データではない |
| 任意のLLM | ローカルOllamaまたはChatGPT接続の一方を指定。指定しなければLLMなし |
| ローカル表示 | HTTPの別画面表示。既定8765番、表示更新400ms、更新停止1.5秒で推奨を取消 |

必要な起動ファイルは校正JSONとカードDB。任意指定はデッキJSON、展開手順JSON、UIルールJSONです。存在確認後に読み込みます。デッキ情報は現在「認識対象IDの絞り込み」であり、採用枚数・残枚数・戦略を自動計算する機能ではありません。

通常runは取得方式を選べますが、agent-loopのライブ取得はMSS固定です。dxcamは負座標モニターの選択に未対応です。

## 2. 1操作の処理順

1. ESC/F9停止、F8一時停止、実行時間、操作回数、対象ウィンドウの前面状態を確認。
2. 操作確認で取得した画像と状態が残っており、観測期限内なら再利用。それ以外はMSSから新しい画像を取得。
3. 全画像と各校正領域を160×90へ縮小し、差分を見る。変化、0.5秒の更新期限、非同期判断完了のいずれかで判断へ進む。通らなければ50ms待つ。
4. 校正領域を切り出して認識。同じ画素の領域は前回結果を再利用し、時刻を新しくする。操作確認済みの同じFrameを使う場合は認識全体を省略。
5. GameStateを構築。ターン、側、フェイズ、LP、手札枚数、ゾーンのカード、prompt、演出、カード状態、表示された操作候補を格納。各観測に値・信頼度・認識元・時刻を持つ。
6. 直前状態との差分を履歴へ追加。上限200件。画面から確認できた変化であり、召喚・破壊などの原因を完全に推論しない。
7. 表示候補を信頼度・鮮度・ターン・フェイズで絞る。カードごとの全合法性は未判定。
8. プランを観測情報から更新。判断は「演出待ち → 登録UIルール → 登録展開手順 → 基準判断」の順。展開手順が選ばれているのに次候補がない場合は原則待機。レシピ自体がない場合は基準判断へ進む。
9. 条件を満たす未解決判断または複数候補に対し、設定されていれば非同期LLMを要求・受領。LLMが選んだ候補を現在状態と照合。
10. 行動がない・信頼度不足なら理由を記録して待機。行動があれば校正領域の中心をデスクトップ座標へ変換。
11. 明示的な操作前待機が設定されている場合は待機後に再取得・再判断。同じ行動が残っているか照合。
12. 観測鮮度を確認し、操作前PNGを同期保存。保存後も期限・停止を確認。
13. 前面、対象ウィンドウの移動・サイズ変更、クリック点の範囲、別ウィンドウの被覆を検査。カーソル移動後にも検査してクリック。
14. 50ms待機 → 取得 → 認識 → 終了・期待する変化の確認を繰り返す。既定の確認期限は3秒。
15. 成功確認後にプランを進める。操作後PNGと状態・時間・結果を記録し、確認画像と状態を次の判断へ渡す。

確認では、まず全画面の平均画素差が0.005以上であることを要求します。その上で信頼できる既知の状態変化、または十分な信頼度の新しい候補集合を要求します。候補が消えたことだけ、既知値が未知になったことだけでは成功にしません。プランに期待カード・prompt・フェイズが指定されていれば追加照合します。

「クリック完了」「画面遷移を確認」「効果が意図どおり解決」「戦略として最善」は別です。現行の成功ログは後二者を一般に証明しません。

## 3. 既定値と注意点

| 項目 | agent-loopの既定 | 注意 |
|---|---|---|
| 操作前固定待機 | 0秒 | --no-fastでは0.5秒。明示した--settle-secondsが優先 |
| 確認・待機周期 | 0.05秒 | 実際は取得・認識時間が加算される。--no-fastでは0.2秒 |
| 確認期限 | 3秒 | 現状CLIに専用の変更引数なし。ブロッキング処理中の厳密な打切りはない |
| 実行上限 | 300秒 / 100操作 | 確認失敗時も送信した操作はカウント |
| 入力の最低信頼度 | 0.98 | 候補生成は既定0.95。UI・プラン・LLMの閾値も別に存在 |
| 観測から入力まで | 最大1秒 | 候補生成の許容年齢は1.5秒だが、入力側の方が厳しい |
| 再試行 | 1 | 新しく観測して再検討。古い座標で単純再送しない |
| 同一操作上限 | 3 | 確認成功後に反復カウントを戻すため、同じボタンへの生涯通算上限ではない |
| 静止画面の再判断期限 | 0.5秒 | run側は1秒。先のLLM完了による即応修正はagent-loop側のみ |
| --fps | 20 | LiveCaptureSourceは値を検査するだけで周期を保持しない。agent-loopも値に基づく制御をしない |
| LLM呼出し上限 | 5回 / 実行 | ターンごとにリセットされない |
| LLM応答期限 | 10秒 | CLIから渡される値。クラス単独の既定値とは違う |
| LLM再要求間隔 | 30秒 | 前回要求の開始時刻から測定。ローカルにも同じ値を適用 |

--fpsを60へ上げるだけでは、agent-loopの取得周期は速くなりません。50msの待機、取得・認識・保存時間が実効速度を決めます。

## 4. 認識・戦略・知識の現在地

### 認識

- テンプレートは64×32へ縮小した色特徴の平均絶対差で比較。最高点と次点の差・閾値で棄却。
- 数値OCRはTesseractを都度サブプロセス起動。灰色画像と二値画像の2通りを認識し、一致と信頼度で採用。1回最大3秒の期限で、領域ごとに最大2回呼ぶ。実際に常に6秒かかるわけではない。
- 画素完全一致のキャッシュ。微細な点滅やハイライトでも再認識対象になる。
- カードIDがDBに存在するときだけカードとして採用。未認識は未知であり、空のゾーンとは区別。
- 固定card_id/targetは特定のUI専用。動く手札や汎用選択一覧へ固定して一般化する仕組みはない。

### 戦略

- UIルールはpromptと表示候補が一意に合う場合に対応。汎用的な「はい」の自動選択はしない。
- プランは必要カード、優先順位、順番、フェイズ、対象、期待結果のJSON。全盤面から最適手順を探索するものではない。
- 相手ターンでも条件一致のレシピを選べるが、ターン側が変わるとリセットして再選択する。将来手札の予測や事前探索結果の引継ぎは未実装。
- 通常のDecisionEngineは認識信頼度順。同点は行動種別・領域名順。勝率、打点、妨害、リソースを評価しない。
- LLMにはGameStateだけを送る。盤面のカードID・名前・種別は含まれるが、DBのeffect_text、関係グラフ、知識Markdown、履歴200件、デッキ全体、展開目標は送っていない。
- LLM要求にはpromptが既知の"none"であることが必要。prompt未知・演出中・プランの入力結果待ちでは呼ばない。候補がない状態では要求しない。
- ローカルLLMは候補番号とconfidenceだけを返す。thinking無効、temperature 0、context 4096、生成上限192、keep_alive 30分を要求する実装。
- LLM回答は時刻等を除いた状態の意味キー、期限、最新の許容候補、信頼度で照合。盤面変化があれば破棄。
- プランpendingがなければ、進行中レシピが待機している一部状況でもLLM経路へ入り得る。レシピと例外判断の権限分担は改善余地がある。

### 接続不足・文書との差

- 知識Markdownは人や開発時の助手向け資料。Pythonの自動実行経路に検索・読込みがない。
- カード関係グラフはCLIの登録・探索まで。Pipeline/TurnPlannerは呼び出していない。条件は文章で、実行可能な効果判定ではない。
- カードDBは読んでDecisionContextに渡すが、現在のDecisionEngineは効果情報を使わない。
- DeckProfileはIDリストのみ。メイン/EX区分・枚数・使用済み効果・召喚権は管理していない。認識ID制限は相手ゾーンにも及ぶので、狭めすぎると相手カードを認識できなくなる。
- 現行GameStateにチェーンスタック、効果IDごとの使用履歴、召喚権、適用中の召喚制限、可変攻撃力の専用構造はない。
- 古いAGENTS/READMEの観測専用記述、設計文書のグラフ込み経路と、現在の入力対応実装・未接続グラフに差がある。本書は実装を基準にする。

## 6. 高速化の優先順位

| 優先度 | 箇所 | 現状・改善案 | 効果の条件 |
|---|---|---|---|
| 最優先 | 待機理由の計測 | 判断なしを、未校正・候補なし・閾値不足・LLM実行中・cooldown・予算切れ・期待結果待ち等に分解 | 計算が遅いのか、情報不足なのかを判別できる |
| 最優先 | 校正・手順の整備 | prompt none、演出、全手札と選択UI、素材/対象、期待結果、分岐を登録 | 未認識で進めない場面を減らす。現在は影響大と推定 |
| 高 | LLM待機制限 | ローカルと外部で予算を分離。状態キー単位の重複抑制、失敗時backoff、予算切れを明示 | 既定では次の曖昧場面で前回開始から最大約30秒待ち得る。5回後は追加要求できない |
| 高 | 確認の全画面差分 | 操作先と期待する結果の領域差分・状態変化を使う | 小さな選択変化は全画面平均0.005未満になり、3秒の確認期限へ進む可能性がある |
| 高 | 画像・ログ保存 | 画像をメモリー上で確保し、上限付きキューで保存処理を分離。失敗通知、終了時drain、容量管理を実装 | 今は前後PNG・JSON書出しが操作ループを止める。所要時間は未測定 |
| 高 | OCR | 数字の認識器常駐または桁テンプレート、必要領域のみ更新、期限付き別処理 | number領域を使用する場合。現存の限定校正はテンプレート中心 |
| 中 | 取得と待機のスケジューラー | --fpsを実装と一致させ、取得時間込みの周期制御。結果が既に到着していれば確認冒頭の固定sleepを省く | 単純なFPS増加より、重複待機の整理を先に行う |
| 中 | 相手ターンの準備 | 自分の公開手札を使う条件付きルートを準備し、ターン開始時に差分検証 | 現行はターン変更でレシピを捨てる。未知のドローや相手手札は確定しない |
| 中 | 差分処理 | 背景を主トリガーにせずUI領域ごとに更新。見た目のノイズを除外するマスクはラベル付き画像で検証 | 演出・背景の変化で全処理へ進む回数を減らす |
| 中 | LLM入力と知識 | 関係カードの効果ID・条件・現在の制限を短い構造へまとめる。変化する時刻等を入力から除去 | 知識全件を毎回送ると遅くなる。現在は必要な効果情報自体が未接続 |
| 中 | モデル準備 | 対戦前の事前読込み、常駐状態・メモリー量・初回/通常推論の別計測 | 現在の起動スクリプトはサーバー起動まででモデルの事前読込みを行わない |
| 低〜中 | 細かな計算 | 重複np.array_equal、SQLite再読込み、JSON化後の再モデル化、全画面float配列生成を削減 | 小規模認識では既に約1msなので実測して優先度を判断 |

必要な計測は、ターン総時間、画面の操作可能状態から入力まで、クリック間隔、確認まで、取得/差分/認識/OCR/判断/PNG/ログの各時間とp50/p95/p99、待機理由別累積秒数、LLM破棄理由、誤操作率、プラン完遂率です。

現在のtotal_compute_msには待機・PNG・入力・確認全体は含まれません。operation_msは入力開始以降であり、操作前PNGを含まず、actionsログの書出しより前に確定します。observation_to_click_msは既に取った画像からの時間で、次の画面を待った時間やターン総時間ではありません。

## 7. ローカルへ保存すべき情報

データは「人が読む根拠」「機械が判定する構造」「画像と検証結果」に分けて対応付けます。Markdownやカード画像を置くだけでは現在のPythonに自動反映されません。以下のうち現在のスキーマを超える項目は、読込と実行コードの追加が必要です。

### A. 実行環境・画面設定（最優先）

- 画面解像度、DPI、ウィンドウタイトル、クライアント矩形、モニター座標、表示モード、言語、UI設定、画像取得方式。
- ターン・フェイズ・LP・手札・盤面・墓地/除外一覧・チェーン表示・終了画面の領域。
- promptなし、演出中/終了、選択可能/不可、選択済み/未選択の正例と紛らわしい負例。
- 手札枚数で変化する配置、カード拡大/ホバー、選択一覧の並べ替え・ページ送り・スクロール位置。
- 各操作について入力点、候補の根拠、押せる条件、成功時の表示、失敗時の表示、通常の待ち時間。
- 校正ID・対象解像度・ゲーム更新版・作成日・独立検証画像ID・誤認率。変化に弱い設定を旧版と混ぜない。

### B. 実デッキ（最優先）

- メイン/EXのカードIDと枚数、使用するデッキ版、先攻/後攻方針。
- 初動、展開補助、妨害、捲り、コスト候補、温存対象の役割。
- 実際に到達可能な最終盤面と必要な素材、使ってよいリソース、残したい後続。
- 自分のデッキ内の残数は初期構成と確認済み移動を根拠に追跡し、不確実なら範囲/未知として保持。相手の未公開採用枚数は確定しない。
- 現行DeckProfileはcard_ids/generic_card_idsだけなので、枚数などは拡張が必要。

### C. カード情報・効果ルール（最優先）

- カードID、名前と別名、種別、属性/種族、レベル/ランク/リンク、基本攻守、公式テキスト。
- 効果をカード単位ではなく効果ID単位で分け、発動場所、条件、コスト、対象、処理、任意/強制、使用制限を構造化。
- 名称単位/個体単位の1ターン制限、発動と使用の区別、複数効果からどちらかを選ぶ制限。
- 召喚条件・素材条件・召喚/攻撃の制限・効果適用の期間・無効や代替処理。
- 出典、確認日、対象ゲーム/版、検証状態。現在のMaster Duelでの使用可否は確認済み版と結び付ける。
- 文章から推定して作った条件には未検証を付ける。現在のCardスキーマは基本属性とeffect_textまで。

### D. 展開レシピ・分岐（最優先）

- 開始条件: 手札の組合せ・枚数、盤面、墓地/除外、召喚権、使用済み効果、適用中制限。
- 各手順: 効果ID、選択カード、対象、素材、コスト、配置、表示形式、確認UI、操作後の期待状態。
- サーチ優先順、素材に使いたくない札、残す妨害、達成盤面、最低保証の着地点。
- 妨害された場所と残った公開リソースに応じた代替ルート、対象不在、効果無効、想定外ドローへの分岐。
- 終了条件、再計画条件、失敗時に押さない条件、残り時間に応じた短いルート。
- 現行PlanBookは直列手順とカード存在条件が中心。枚数・不在・使用済み効果・汎用の分岐グラフは拡張対象。

### E. UI操作辞書（最優先）

- 同じ「はい/いいえ」でも、効果発動、追加効果、破壊代替、チェーン確認などの意味を別IDにする。
- 選択カード一覧とカードIDの対応、ページ位置、素材/対象/コストの種別、必要選択数、残り選択数。
- 単一クリック、選択解除、確定、キャンセル、戻る、配置選択の違い。
- 次に出る可能性のある画面と、それぞれで見る領域・成功条件。
- 後続UIを予測しても、表示前に連続クリックしない。表示を確認してから登録手順を実行する。

### F. 対戦中の事実と履歴（高）

- 現在のターン、チェーン、発動元、コスト支払い、対象、解決状況。
- 自分の召喚権、カード/効果IDごとの使用履歴、召喚・攻撃制限、期限付きの効果。
- 確認済みのカード移動、表裏・表示形式、既知の相手カード、無効状態、現在の攻守。
- 「未観測」「空」「候補が複数」「以前は見えていたが現在は不明」を区別。
- 観測事実と推論を分け、推論には根拠と信頼度を保存。古い観測を現在のクリック根拠にしない。
- 現在のTrackerは最大200件の差分であり、この意味付き履歴は未実装。

### G. 対面知識と妨害判断（高）

- 公開カードから識別できるテーマの根拠、候補テーマと確度。
- そのカードのどの効果を止めるか、止めると止まる経路、既に見えている代替経路。
- 相手の公開妨害、回数、対応可能な効果、踏ませる順序。
- 自分の妨害を温存する条件と使う条件、対象不在・無効化される状況。
- 単なるテーマ名から相手手札や採用枚数を確定しない。現在の実行経路へ接続するには構造化と判定コードが必要。

### H. 探索・評価・キャッシュ（中〜高）

- サーチ/蘇生/素材等の関係グラフを、カード名だけでなく効果ID・条件・必要リソースと結び付ける。
- 初手/公開盤面に対する検証済みルート、コスト、到達盤面、妨害数、後続、手順数、平均所要時間。
- 勝ち切れる根拠を含む攻撃順・打点計算、継続不能の枝の除外条件。
- キャッシュキーにデッキ版、ルール版、使用済み効果、制限、公開状態を含める。単に同じカード名なら同じ手を返す方式にしない。
- 相手ターンに準備したルートは開始時に条件を再検証して採用する。

### I. 検証データ・失敗データ（高）

- 別の対戦や別場面から取った正解付き画像、演出中/暗転/誤認しやすい画面。
- 状態、許容候補、実行した手、実際の結果、人が確認した評価、失敗理由、各所要時間。
- 正解ラベルの付与者/根拠、学習・検証データの分離、校正に使った画像かどうか。
- 実行が成功したことと戦略的に正しいことを分離。勝った対戦の全操作を自動的に最善手としない。
- 再生可能な一連の操作シナリオ、期待する状態遷移、処理時間と誤操作の回帰検査。

### J. ローカルモデル・運用（中）

- モデル名/版、入力スキーマ版、プロンプト版、生成設定、初回と通常時の測定。
- 事前読込みの結果、メモリー使用状況、タイムアウトと再試行方針、拒否・破棄された回答。
- 関連カードとルールだけを検索して渡す索引。大きな知識集を毎判断の入力に丸ごと入れない。
- LLMの回答は無審査で永続ルールにせず、再生検証・人の確認を経てレシピへ昇格する。

## 8. 推奨する作業順

1. 待機理由とPNG/ログ/確認時間を計測できるようにする。
2. 実デッキ1つと、その代表的な展開1本について、全画面遷移・候補・期待結果を完成させる。
3. 確認を操作別にし、小さなUI変化を捉える。画像保存を分離する。
4. ローカルLLMの再要求間隔・予算・事前読込みを専用設定にする。
5. 効果使用履歴、召喚権、制限を状態へ追加し、妨害時の代替ルートを登録する。
6. 事前計算と必要な知識の検索を接続し、未登録の場面だけLLMへ回す。
7. 実対戦の手順完遂率・誤操作率・ターン総時間で比較し、必要な場合に取得方式やモデルを変更する。
