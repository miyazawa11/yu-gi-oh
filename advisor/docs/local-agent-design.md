# 高速ローカルエージェントの設計

## 全体構成と技術選定

通常経路はMSS/DXCam取得 → ROI差分 → OpenCVテンプレート/必要時OCR → Pydantic状態 → UIルール → 確認付きコンボ → ローカルルール/カードグラフ → 入力直前の照合 → OS入力 → 結果確認です。LLMは未知の戦略に対する任意の非同期サービスとして分離します。毎クリックの画像送信・API呼出しは通常経路に含めません。

既存の `src/master_duel_advisor/` を維持します。`capture.py` が取得、`perception.py`/`regions.py` が認識とROI、`models.py` が型、`tracking.py` が差分、`rules.py`/`planning.py`/`decision.py` が判断、`agent_loop.py` が実行確認、`safety.py` が入力制約、`advisor.py` がローカル表示を担当します。小規模の既存コードを機械的に多数のディレクトリへ分割せず、責務をモジュール単位で分離します。

Python 3.12、NumPy/OpenCV、Pydantic、SQLiteは導入済みです。MSSは負座標の別モニターに対応します。DXCamは現状主モニターのみ。固定UIはテンプレート優先、Tesseractは数値だけの任意依存で、未導入なら未知を返します。高速経路で未変化ROIを再認識しません。入力とホットキーはWindows標準APIを使い、PyAutoGUI/pynputの追加依存を不要にします。カードグラフはSQLiteの有向辺として保存し、限定深さの探索を標準Pythonで実行します。NetworkXは高度な解析が必要になった時の候補、Neo4jは常駐サーバーが必要でこの規模のMVPに不向きです。

## 状態・行動・状態機械

GameStateは取得時刻/連番、ターン/フェイズ/プレイヤー、LP、各ゾーンのカード観測、現在の操作候補を持ちます。手札/墓地/除外はzoneの接頭辞で管理します。各観測は未知値、confidence、認識元、時刻を保持します。非公開カードの正体・未表示の墓地・採用枚数を推測しません。UI promptとアニメーションは独立した校正領域から観測します。

Actionは種類、カードID、対象、認識領域、confidence、観測時刻です。Strategyは座標を直接扱いません。校正済み領域の中心を実行層で画面座標へ変換します。UIルールは登録したpromptに対応する候補だけを選び、Yes/Noを無条件で押しません。

制御状態はOBSERVING、PAUSED、BLOCKED、ACTING、VERIFYING、STOPPEDです。F8は押下の立ち上がりでPause/Resume、F9とESCは停止をラッチします。Pause解除・前面復帰後は新フレームを取得します。対象タイトルから特定したWindowsのハンドルが前面でなければ入力を禁止し、対象の現在のクライアント領域と取得矩形の両方に収まる点だけを許可します。入力直前にもう一度前面と停止状態を検査します。

コンボは各操作の後に状態を確認して進みます。期待条件が違う場合は中断/再検討し、認識喪失だけで成功としません。未知の盤面を前の既知値で上書きしません。未解決の入力結果は記録して再観測します。

## 性能と記録

20FPSを初期値とし、通常判断の開始0.1〜0.5秒、取得20ms未満、認識100ms未満、判断10ms未満、LLMなし計算200ms未満を目標にします。実測値と目標を区別します。取得、認識、判断、入力送信、結果確認、合計の時間を記録します。画像保存/待機を含む操作全体の時間を、判断時間と混同しません。記録には操作前後の状態・画像・候補・行動・信頼度・プランを含め、後でstate→actionの教師データへ変換できます。

## Phase 1の受入条件

画面取得、校正されたUI候補、座標変換、前面/領域/停止ガード、F8/F9、1操作後の確認、ローカルログを実装してユニットテストします。次に実画面の指定ボタンで認識→入力→確認を検証します。模擬入力の成功だけで実機完了とは扱いません。

Phase 2以降は手札/カード状態・promptの校正、期待状態付きコンボ、優先度ルール、グラフ、例外用LLM、表示と記録の順に接続します。現在の1デッキ設定・実カード/全ダイアログ参照は不足しています。実画面の独立した検証を各Phaseのゲートとして残します。
