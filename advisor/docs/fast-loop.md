# 展開手順と高速ローカルループ

## 判断の10秒上限

認識処理の開始から非同期戦略の待ち時間までを含め、1回の判断の期限を10秒に固定します。フレームが更新されても、AI回答待ちの同じ判断の期限は延長しません。期限に達したらAI回答を破棄し、最新の許容候補から認識信頼度が最も高い行動を強制選択します。同点は行動種別・領域名順です。勝率を算出する機能ではありません。

強制選択は信頼度0.98以上・1秒以内の観測・現在の限定ルールで許容される候補が対象です。演出中・終了画面・候補なしでは座標を推測しません。入力直前の鮮度・前面・領域検査は継続します。LLMの再要求制限・呼出し予算・破棄済み通信の処理中で要求できない場合は、待機せず同じ選択処理へ移ります。

`--llm-timeout` は0より大きく10秒以下のみ指定でき、短く設定するとその期限で強制選択へ移ります。OCRには判断全体の残り時間を渡し、操作後の確認OCRにも確認期限を渡します。10秒はソフトウェア上の判断期限であり、Windowsのスケジューリング、停止しないOS処理、画像保存、ゲーム演出、入力完了の時間を保証するものではありません。通常の期限検出には確認周期（既定50ms）等の遅れがあり得ます。

ログの `planner_source=forced_choice` と理由で強制選択を識別でき、候補を確認できない場合は `decision_no_candidate` です。`decision_elapsed_ms` は認識開始からの待ち時間込み、`decision_limit_ms` は10000です。通信自体を強制終了できない場合も、その遅着回答は採用せず、並行ワーカーを増やしません。

`--plan-book` でターンの方針と展開手順を登録します。相手ターンにも公開された自分の手札・盤面から優先度順に準備し、自分の対応フェイズで表示された候補だけを実行します。相手の公開ゾーンが変化した時は残っている認識済みカードから再検討します。任意の対面を理解する戦略 AI ではなく、登録された分岐を使う決定的なプランナーです。

```powershell
.\.venv\Scripts\python.exe -X utf8 -m master_duel_advisor agent-loop --rect=-1920,785,-640,1585 --calibration data/layout.json --database data/cards.sqlite3 --plan-book data/plan-book.json --fast --fps 20 --max-seconds 1800 --output artifacts/fast-agent
```

上記は必要な実画面校正を用意した後の起動例です。今回ライブ操作は起動していません。ESCで停止します。時間・操作回数・信頼度・再試行上限は従来通り有効です。高速設定は既定で有効です（`--fast` は省略可能）。操作前の固定待機は0秒、確認周期は0.05秒です。`--no-fast` で従来の固定待機0.5秒・確認周期0.2秒に戻せます。画面の演出・応答時間と認識負荷に依存するため、クリック間隔1秒以内を保証しません。`--settle-seconds` と `--verify-poll-seconds` の明示指定は高速設定より優先します。

## 校正と手順の作成

`config/plan-book.example.json` は超雷龍召喚の途中を示す編集用の例です。そのまま実対戦へ投入できる完成済み設定ではありません。実画面の配置に応じて、カードを開く・召喚位置・表示形式・素材・対象・確認をそれぞれ1ステップに分け、実際の順番へ編集してください。全てのクリックに表示 UI の独立したテンプレートが必要です。

各 `requires` は `side`（既定self）、`zone_prefix`、`card_id` です。手札は `self.zones.hand_0` などとしてカード認識を校正します。カードIDは取り込んだカードDBのIDと一致させます。レシピの `requires` は開始条件、各ステップの `requires` は進行条件です。効果の解決、素材・対象が残ったことなどは次のステップの現在画面で確認します。未知情報や過去のカード位置を現在の事実として補完しません。

操作領域には従来の `rect`・`exemplars` に加え、任意の `card_id`・`target` を設定できます。これはその領域専用の意味付けです。カードや対象が入れ替わる汎用ボタンには固定IDを設定しないでください。カード・対象・選択済み状態まで含む専用テンプレートを作り、同じ位置の別カードが誤一致しないよう独立した画像で評価してください。

ステップは `type` と `source_region`、任意の `card_id`・`target` が一致する現在の候補を一意に選びます。候補がない・条件が不明・候補が複数なら非操作で待機します。プランモードでは適当に別の候補を実行するフォールバックはありません。未知の手札や対面はレシピ追加と判断が必要です。`priority` による分岐は明示された条件内だけで働き、隠れたカード・採用枚数・勝ち切れるダメージを推測しません。

## 確認と速度の仕組み

- 手順は操作を送信した時には進まず、認識された状態または次の候補UIへの変化を確認して進みます。候補が消えただけ・既知値が未知になっただけでは成功と扱いません。
- 領域の画素が完全一致する時だけテンプレート/OCR結果を再利用し、観測時刻は現在の取得時刻に更新します。微小な変化も再認識します。
- 静止画面の全処理は領域差分と0.5秒の更新期限で抑制します。ただし非同期の戦略判断が完了した場合は、次の取得画像で即座に照合し、更新期限を待ちません。盤面・候補・信頼度・応答期限の検査は維持します。
- 操作後の確認画像と認識結果を次の判断に使い、余分な取得と二重認識を減らします。取得画像を更新した場合は認識結果を破棄します。判断と手順の更新は毎回実行し、再利用時は `metrics.perception_reused=true` を記録します。
- 操作前に待機した場合は再認識し、候補を照合します。1秒以上古い観測ではクリックしません。待機中の画面変化で以前の座標を使い回しません。
- 非操作フレームの画像保存を省き、実際の操作前後だけ記録します。`actions.jsonl` に `observation_to_click_ms` とプラン、`agent-run.json` にp95を記録します。これは取得時刻からクリック呼出しまでで、物理画面変化からの遅延やクリック間隔ではありません。
- 通常の観測/replayも `--plan-book` を指定できます。操作なしで手順を検討でき、確認フィードバックを受けるまで次へ進みません。

実ゲームのカード/ボタン/終了表示校正と独立評価は未完了です。合成デモや模擬クリックの速度を実ゲームの性能として扱いません。
